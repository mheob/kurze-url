# Backups Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The production database can be restored from an encrypted off-site copy after Supabase loses it, after the account is lost, or after the maintainer destroys it by hand.

**Architecture:** A daily GitHub Actions workflow in a **separate private repository** dumps `public`, the `auth` data and the cluster roles with the Supabase CLI, asserts the dump actually contains what it should, encrypts it with an `age` public key, and uploads it as a release asset in that same repository. A second step prunes to fourteen daily plus twelve weekly copies using nothing but the dates in the tags. A Better Stack heartbeat watches for the absence of a backup rather than the failure of a job. The restore procedure is published in the public repository, because a recovery procedure stored inside the system you are recovering from is unreachable when you need it.

**Tech Stack:** GitHub Actions, Supabase CLI (`supabase db dump`), PostgreSQL `pg_dump` via the session pooler, `age`, `gh` CLI, Python 3 (standard library only), Better Stack heartbeats.

**Spec:** `docs/superpowers/specs/2026-09-07-backups-design.md`

## Global Constraints

- **Two repositories.** Tasks 1, 3 and 4 create files in a **private** repository, assumed to be named `kurze-url-backups` and cloned as a sibling of this one at `../kurze-url-backups`. Tasks 5 and 8 touch the public `kurze-url` repository. Every task states which. Never put a production database URL in the public repository.
- **The success criterion** the whole plan serves: given only the encrypted backup and the private key, a fresh Supabase project can be brought to a state where the existing production frontend, pointed at it, lets a previously registered maintainer log in and see their teams and links.
- **Backups are of production only.** Redis, the preview database, and all platform configuration are deliberately out of scope.
- **The workflow encrypts but can never decrypt.** Only the `age` **public** key is ever a secret in CI. A compromised run may append, never read.
- **`supabase db dump`'s schema dump excludes `auth`; its data dump includes it.** Both behaviours are wanted and neither should be overridden with `--schema`.
- **A restore needs six environment variables across two Vercel projects**, not just data: `DATABASE_URL`, `SUPABASE_JWKS_URL`, `SUPABASE_JWT_ISSUER`, `SUPABASE_SERVICE_ROLE_KEY` on `kurze-url-api`; `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` on `kurze-url-web`.
- **Retention: keep everything younger than 14 days; keep the earliest backup of each ISO week up to 84 days; delete the rest.**
- Commits: Conventional Commits, **max 50 characters including type and scope**, no co-author or generator footer. In the public repository all git writes go through GitButler (`but commit -b <branch>`), never `git add`/`git commit`. The private repository is a plain git checkout and uses plain git.
- In the public repository, run `pnpm format` before committing and never bypass the Lefthook hooks.

```yaml
# before anything is built on the answer: can a GitHub Actions runner,
# which is IPv4-only, produce a complete dump from Supabase, whose direct
# connection is IPv6?
name: probe

  workflow_dispatch:

permissions:
  contents: read

jobs:
  probe:
    runs-on: ubuntu-latest
    steps:
      - uses: supabase/setup-cli@v1
        with:
          version: latest

      - name: Dump
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
        run: |
          mkdir -p dump
          supabase db dump --db-url "$DATABASE_URL" --role-only -f dump/roles.sql
          supabase db dump --db-url "$DATABASE_URL" -f dump/schema.sql
          supabase db dump --db-url "$DATABASE_URL" --data-only --use-copy -f dump/data.sql

      - name: Report what came out

          wc -c dump/*.sql
          echo "--- does the schema carry the application tables? ---"
          grep -c 'CREATE TABLE IF NOT EXISTS "public"."link"' dump/schema.sql || true
          echo "--- does the data carry the users? ---"
          grep -c 'COPY "auth"."users"' dump/data.sql || true
```

### Task 3: The backup workflow

**Repository:** private `kurze-url-backups`

**Files:**

- Create: `.github/workflows/backup.yml`
- Create: `README.md`
- Delete: `.github/workflows/probe.yml`

**Interfaces:**

- Consumes: the secrets `DATABASE_URL`, `AGE_PUBLIC_KEY`, `BACKUP_HEARTBEAT_URL`.
- Produces: one release per run, tagged `backup-YYYY-MM-DD`, carrying one asset named `kurze-url-YYYY-MM-DD.tar.gz.age`. Task 4 prunes those releases and depends on that exact tag format.

**A deliberate divergence from the spec.** The spec calls for "a size floor" on the three files. This task asserts on **content** instead — that the schema carries `public.link` and `public.team`, and that the data carries `auth.users` and `public.team`. A byte count only catches a file that is empty; a content check also catches a dump that connected to the wrong database, lost the `auth` schema, or silently produced a schema with no tables. The floor survives only for `roles.sql`, where there is no distinctive string worth matching.

- [ ] **Step 1: Write the workflow**

Create `.github/workflows/backup.yml`:

```yaml
# The daily backup of the kurze-url production database.
#
# Two properties are load-bearing and easy to erode:
#
#   - This job encrypts but cannot decrypt. Only the age PUBLIC key is a
#     secret here, so a compromised run can append a backup but cannot read
#     any that already exist. Never add the private key to this repository.
#   - The heartbeat is pinged only after everything else has succeeded, and
#     Better Stack alerts on its absence. That covers the run that failed and
#     the run that never started — and the second one is the likely failure,
#     because GitHub disables scheduled workflows after 60 days without
#     repository activity and a backup repository has none by construction.
name: backup

on:
  schedule:
    # Not on the hour: GitHub queues every scheduled job at :00 and runs the
    # backlog late. 03:23 UTC is also outside the keep-alive workflow's
    # 04:17, so the two never contend for the same database.
    - cron: '23 3 * * *'
  workflow_dispatch:

concurrency:
  group: backup
  cancel-in-progress: false

permissions:
  # Creating releases and uploading assets. GITHUB_TOKEN is scoped to this
  # repository, which is exactly why the workflow lives here rather than in
  # the public one, where it would need a personal access token.
  contents: write

jobs:
  backup:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: supabase/setup-cli@v1
        with:
          version: latest

      - name: Install age
        run: sudo apt-get update && sudo apt-get install -y age

      - name: Dump
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
        run: |
          mkdir -p dump
          # Three dumps, restored in this order. The schema dump excludes the
          # auth schema (a fresh project brings its own, correctly versioned)
          # and the data dump includes it (the user rows are what must come
          # back). Both are the CLI's defaults; do not pass --schema.
          supabase db dump --db-url "$DATABASE_URL" --role-only -f dump/roles.sql
          supabase db dump --db-url "$DATABASE_URL" -f dump/schema.sql
          supabase db dump --db-url "$DATABASE_URL" --data-only --use-copy -f dump/data.sql

      - name: Assert the dump contains what a restore needs
        run: |
          # Content assertions, not byte counts. A backup that is reliably
          # uploaded and reliably empty is the canonical way to discover on
          # the worst day that there were never any backups.
          fail=0
          check() {
            if grep -q "$2" "$1"; then
              echo "ok   $1 contains $2"
            else
              echo "FAIL $1 does not contain $2" >&2
              fail=1
            fi
          }
          test -s dump/roles.sql || { echo "FAIL dump/roles.sql is empty" >&2; fail=1; }
          check dump/schema.sql 'CREATE TABLE IF NOT EXISTS "public"."link"'
          check dump/schema.sql 'CREATE TABLE IF NOT EXISTS "public"."team"'
          check dump/data.sql 'COPY "auth"."users"'
          check dump/data.sql 'COPY "public"."team"'
          if [ "$fail" -ne 0 ]; then
            echo "Refusing to upload an incomplete dump." >&2
            exit 1
          fi

      - name: Encrypt
        env:
          AGE_PUBLIC_KEY: ${{ secrets.AGE_PUBLIC_KEY }}
        run: |
          if [ -z "$AGE_PUBLIC_KEY" ]; then
            echo "AGE_PUBLIC_KEY is not set" >&2
            exit 1
          fi
          DATE=$(date -u +%F)
          echo "DATE=$DATE" >> "$GITHUB_ENV"
          tar czf - -C dump . | age -r "$AGE_PUBLIC_KEY" -o "kurze-url-$DATE.tar.gz.age"
          ls -l "kurze-url-$DATE.tar.gz.age"

      - name: Upload as a release
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          gh release create "backup-$DATE" "kurze-url-$DATE.tar.gz.age" \
            --title "backup-$DATE" \
            --notes "Encrypted dump of the production database. Restore procedure: https://github.com/mheob/kurze-url/blob/main/docs/restore.md"

      - name: Heartbeat
        env:
          BACKUP_HEARTBEAT_URL: ${{ secrets.BACKUP_HEARTBEAT_URL }}
        run: curl --fail --silent --show-error --max-time 10 "$BACKUP_HEARTBEAT_URL"
```

- [ ] **Step 1: Write the failing test**

Create `scripts/test_prune.py`:

```python
"""Tests for the pruning decision.

This logic deletes backups. A bug here is not a broken build, it is three
months of history gone, discovered later. Every case below is one specific
way it could be wrong.
"""

import unittest
from datetime import date, timedelta

from prune import tags_to_delete

TODAY = date(2026, 9, 7)  # a Monday


def tag(days_ago: int) -> str:
    return "backup-" + (TODAY - timedelta(days=days_ago)).isoformat()


def decide(*days_ago: int) -> set[str]:
    return set(tags_to_delete([tag(d) for d in days_ago], today=TODAY))


class PruneTest(unittest.TestCase):
    def test_everything_within_fourteen_days_is_kept(self):
        self.assertEqual(decide(*range(0, 15)), set())

    def test_each_older_iso_week_keeps_its_earliest(self):
        # 2026-09-07 is a Monday, so days 20 and 21 back fall in ISO week 34
        # and days 22 to 26 in week 33. Two survive, one per week: day 21
        # (2026-08-17) and day 26 (2026-08-12). The bug this catches is a rule
        # that keeps one backup per rolling period rather than one per week,
        # which looks identical until a week boundary lands inside the range.
        kept = {tag(21), tag(26)}
        deleted = decide(*range(20, 27))
        self.assertEqual(deleted, {tag(d) for d in range(20, 27)} - kept)

    def test_a_week_older_than_eighty_four_days_is_deleted_entirely(self):
        self.assertEqual(decide(85, 86, 87), {tag(85), tag(86), tag(87)})

    def test_the_boundary_day_is_kept(self):
        # Exactly 84 days old, and the only backup of its week.
        self.assertEqual(decide(84), set())

    def test_an_unparseable_tag_is_never_deleted(self):
        # A tag this script does not understand is somebody else's. Leaving
        # it alone is the only safe default.
        self.assertEqual(set(tags_to_delete(["v1.0.0", "backup-nope"], today=TODAY)), set())

    def test_an_empty_list_deletes_nothing(self):
        self.assertEqual(set(tags_to_delete([], today=TODAY)), set())

    def test_a_single_old_backup_survives_as_its_weeks_earliest(self):
        # The dangerous bug: pruning that deletes the only copy left.
        self.assertEqual(decide(40), set())


if __name__ == "__main__":
    unittest.main()
```

Create `scripts/prune.py`:

```python
#!/usr/bin/env python3
"""Decide which backup releases to delete.

Reads `gh release list --json tagName` output on stdin, prints the tags to
delete on stdout, one per line. It deletes nothing itself: the workflow pipes
this into `gh release delete`, so the decision can be tested without a network
and inspected without consequences.

The rule, from the spec:

  - younger than 14 days      -> keep
  - up to 84 days, and the earliest backup of its ISO week -> keep
  - otherwise                 -> delete

Deriving everything from the date in the tag means there is no bookkeeping to
drift out of step, and a missed run leaves no broken chain.
"""

import json
import sys
from datetime import date

PREFIX = "backup-"
DAILY_DAYS = 14
WEEKLY_DAYS = 84


def _parse(tag: str) -> date | None:
    """The date in a backup tag, or None if this is not one of ours."""
    if not tag.startswith(PREFIX):
        return None
    try:
        return date.fromisoformat(tag[len(PREFIX) :])
    except ValueError:
        return None


def tags_to_delete(tags: list[str], today: date) -> list[str]:
    dated = [(t, d) for t in tags if (d := _parse(t)) is not None]

    # The earliest backup of each ISO week is the one that represents it.
    earliest_of_week: dict[tuple[int, int], date] = {}
    for _, d in dated:
        week = d.isocalendar()[:2]
        if week not in earliest_of_week or d < earliest_of_week[week]:
            earliest_of_week[week] = d

    doomed = []
    for tag, d in dated:
        age = (today - d).days
        if age <= DAILY_DAYS:
            continue
        if age <= WEEKLY_DAYS and earliest_of_week[d.isocalendar()[:2]] == d:
            continue
        doomed.append(tag)
    return doomed


def main() -> None:
    releases = json.load(sys.stdin)
    tags = [r["tagName"] for r in releases]
    for tag in tags_to_delete(tags, today=date.today()):
        print(tag)


if __name__ == "__main__":
    main()
```

- [ ] **Step 1: Write the restore procedure**

Create `docs/restore.md`:

````markdown
# Restoring the database

The production database is backed up nightly to a **private** repository, `kurze-url-backups`, as an encrypted release asset. This procedure turns one of those assets back into a running instance.

It lives here, in the public repository, on purpose: a recovery procedure stored only inside the system you are recovering from is unreachable exactly when you need it. Nothing below is secret. The secrets are the database URL and the `age` private key, and both live elsewhere.

## What you need

- The `age` **private** key. Without it every backup is unreadable, and no backup contains it. You stored two copies in separate places.
- `age`, the `supabase` CLI, `psql`, and `gh`.
- Access to the Supabase account and both Vercel projects.

## What a restore does not bring back

Sessions. Password hashes travel with the dump, so everyone can log in again — but everyone is logged out, because a fresh project signs tokens with new keys.

## Procedure

### 1. Fetch the newest backup

```bash
gh release list --repo mheob/kurze-url-backups --limit 5
gh release download backup-YYYY-MM-DD --repo mheob/kurze-url-backups
```

### 2. Decrypt and unpack

```bash
age -d -i /path/to/backups-key.txt -o backup.tar.gz kurze-url-YYYY-MM-DD.tar.gz.age
mkdir -p restore && tar xzf backup.tar.gz -C restore
ls -l restore   # roles.sql, schema.sql, data.sql
```

### 3. Create a fresh Supabase project

Frankfurt/EU region — the same choice `docs/planning/08-legal-and-compliance.md` argues for, and not one to re-decide under pressure.

Note its project ref, its database password, and its connection strings.

### 4. Apply the three files, in this order

```bash
psql "$NEW_DATABASE_URL" --single-transaction --variable ON_ERROR_STOP=1 -f restore/roles.sql
psql "$NEW_DATABASE_URL" --single-transaction --variable ON_ERROR_STOP=1 -f restore/schema.sql
psql "$NEW_DATABASE_URL" --single-transaction --variable ON_ERROR_STOP=1 -f restore/data.sql
```

Order is not cosmetic: roles are referenced by the schema, and the schema is referenced by the data. `ON_ERROR_STOP=1` matters as much — without it `psql` reports success after skipping every statement that failed.

The schema file deliberately does not contain the `auth` schema; the new project brought its own. The data file deliberately does contain `auth` data, which is how the users come back.

### 5. Repair the migration history

```bash
supabase link --project-ref <new-ref>
supabase migration list
```

The dump does not carry `supabase_migrations`, so the restored project has a complete schema and an empty history. Left alone, the Supabase GitHub integration would try to apply every migration again on the next merge to `main` and damage what you just recovered.

Mark every migration already present as applied:

```bash
supabase migration repair --status applied <version>
```

Repeat for each version `supabase migration list` shows as local-only, then run `supabase migration list` again and confirm both columns match.

### 6. Reconfigure the new Supabase project

Two things live in project settings rather than in Postgres, and both fail quietly:

- **Resend as custom SMTP.** Without it Supabase's built-in sender caps at two mails an hour, and team invitations silently stop arriving.
- **Auth redirect URLs and the site URL**, pointing at `https://www.kurze-url.app`.

### 7. Repoint both Vercel projects

Six variables. Missing any of them leaves a working database nobody can use.

| Project | Variable | New value |
| --- | --- | --- |
| `kurze-url-api` | `DATABASE_URL` | the new project's transaction pooler URL, port 6543 |
| `kurze-url-api` | `SUPABASE_JWKS_URL` | `https://<new-ref>.supabase.co/auth/v1/.well-known/jwks.json` |
| `kurze-url-api` | `SUPABASE_JWT_ISSUER` | `https://<new-ref>.supabase.co/auth/v1` |
| `kurze-url-api` | `SUPABASE_SERVICE_ROLE_KEY` | the new project's service-role key |
| `kurze-url-web` | `SUPABASE_URL` | `https://<new-ref>.supabase.co` |
| `kurze-url-web` | `SUPABASE_PUBLISHABLE_KEY` | the new project's publishable key |

Redeploy both projects afterwards; environment variables are read at runtime, but the deployment has to be replaced for them to take effect.

### 8. Confirm the restore actually worked

Not "the data is there" — that is the easy half:

1. `curl -sI https://go.kurze-url.app/<a known slug>` returns a 301 or 302 to the right destination.
2. Log in at `https://www.kurze-url.app` **as an account that existed before the backup**, with its existing password or magic link.
3. That account sees its teams and its links.

Step 2 is the whole point. A restore that stops at step 1 has proven only that Postgres accepted the file.

### 9. Point the backup workflow at the new database

Update `DATABASE_URL` in the `kurze-url-backups` repository's secrets to the new project's **session pooler** string, and run the workflow by hand once. A restored instance that is no longer being backed up is one incident from the same position again.

## Drill
````

- [ ] **Step 2: Write the local restore script**

Create `scripts/restore-local.sh`:

```bash
#!/usr/bin/env bash
# Apply a decrypted backup to the local Supabase stack.
#
# This is the cheap, repeatable half of the restore drill: it proves the three
# files apply cleanly and the user rows arrive. It cannot prove anyone can log
# in to a hosted project — that needs the real procedure in docs/restore.md.
#
# Usage: scripts/restore-local.sh <directory containing roles.sql schema.sql data.sql>
set -euo pipefail

DUMP_DIR="${1:?usage: restore-local.sh <dump-directory>}"
LOCAL_DB="postgres://postgres:postgres@127.0.0.1:54322/postgres"

for f in roles.sql schema.sql data.sql; do
	if [ ! -s "$DUMP_DIR/$f" ]; then
		echo "missing or empty: $DUMP_DIR/$f" >&2
		exit 1
	fi
done

if ! pg_isready -d "$LOCAL_DB" >/dev/null 2>&1; then
	echo "local Supabase is not running — start it with 'supabase start'" >&2
	exit 1
fi

# ON_ERROR_STOP is the point of this script. Without it psql reports success
# after skipping every statement that failed, which is how a restore gets
# declared working when it is not.
for f in roles.sql schema.sql data.sql; do
	echo "applying $f"
	psql "$LOCAL_DB" --single-transaction --variable ON_ERROR_STOP=1 -f "$DUMP_DIR/$f"
done

echo
echo "row counts after restore:"
psql "$LOCAL_DB" --no-psqlrc --tuples-only --command \
	"select 'auth.users', count(*) from auth.users
	 union all select 'team', count(*) from public.team
	 union all select 'link', count(*) from public.link;"
```

Make it executable:

```bash
chmod +x scripts/restore-local.sh
```

## Closing checklist

What the tests prove:

- [ ] `python3 -m unittest test_prune` is green, and each retention constant has been shown to break a specific test
- [ ] The backup workflow's content assertions have been watched failing, with no release created
- [ ] A real backup applies to a clean local Supabase with non-zero `auth.users`, `team` and `link` counts

What only running the thing proves, and what a maintainer therefore confirms by hand:

- [ ] A release with a `.age` asset appears after a scheduled run, not only after a manual one
- [ ] The Better Stack heartbeat is green, and goes red when a run is skipped
- [ ] Someone who existed before the backup can log in to a restored instance
- [ ] The prune step deletes nothing while fewer than fifteen backups exist
- [ ] The `age` private key exists in two places, and both are written down somewhere the maintainer will find them in a year

Deferred by design, and worth revisiting only if the assumption changes:

- [ ] Release-asset storage on private repositories is assumed to have no practical ceiling here, because the dumps are kilobytes to low megabytes. Revisit if that stops being true.
- [ ] The drill repeats annually. Nothing enforces that; it is a calendar entry, not a workflow.
